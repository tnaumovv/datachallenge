# CQA — контроль качества диалогов

Backend для оценки качества диалогов: TypeScript, Express 5, Zod, SQLite и официальный SDK Gemini. Реализованы импорт, версии транскриптов и чек-листов, AI-оценщик с проверкой доказательств, очередь, сохранение результатов и расчёт баллов. Реальное подключение модели требует API-ключа и проверки доступа. Апелляции доступны в API. Веб-интерфейс показывает транскрипт, чек-лист и результат проверки с цитатами.

## Запуск

Рекомендуется Node.js 24 (`nvm use`). Используется встроенный `node:sqlite`; на некоторых версиях Node он выводит предупреждение ExperimentalWarning. База — обычный локальный SQLite-файл, отдельный сервер БД не нужен.

```sh
npm ci
cp .env.example .env
npm run dev
```

Если `.env` уже настроен, не заменяйте его. API: `http://127.0.0.1:3000/api/health`.

Для organizer-импорта укажите в `ORGANIZER_API_URL` полную ссылку GET DEV из PDF, включая её query-параметры. Это серверная настройка; её нельзя передавать во фронтенд или коммитить. В текущей рабочей копии она уже настроена, а DEV импортирован в `runtime/cqa.sqlite`.

```sh
npm test
npm run typecheck
npm run build
npm start
```

`npm start` запускает собранный API. `npm run dev` перезапускает сервер при изменениях исходников. Папки `.env`, `runtime`, `work`, `node_modules`, `dist` игнорируются Git. Не запускайте dev и start одновременно на одном порту.

## Экран проверки

Сначала запустите API командой `npm run dev`. В другом терминале выполните `npm run dev:web` и откройте адрес, который выведет Vite. По умолчанию прокси направляет запросы `/api` на `http://127.0.0.1:3000`. Если API запущен на другом локальном порту, задайте `CQA_API_URL` перед запуском Vite.

Экран `/dialogs` показывает уже импортированные диалоги. Выберите диалог и версию чек-листа, чтобы открыть сохранённую оценку или запустить новую при настроенном провайдере. Цитата в правой панели ведёт к соответствующей реплике. Адрес карточки сохраняет выбранную оценку и реплику при обновлении страницы.

`npm run build` собирает сервер и веб-интерфейс. Для просмотра собранного интерфейса запустите API и `npm run preview:web`.

## Контракт для фронтенда

Импортируйте типы через `import type` из `shared/contracts.ts`. Для проверки входа в браузере можно импортировать соответствующую Zod-схему. Только `server` обращается к SQLite и источнику организаторов. Настройте dev proxy Vite: `/api` → `http://127.0.0.1:3000`; CORS на backend не требуется при работе через этот proxy.

| Метод и маршрут | Тело / ответ |
| --- | --- |
| `GET /api/health` | `{status:"ok"}` |
| `POST /api/import` | `ImportRequest` → `ImportResult`; 201 при новых записях, 200 при повторе |
| `GET /api/conversations` | `Conversation[]`; фильтры `groupId`, `language`, `channel` |
| `GET /api/conversations/:id` | `Conversation` |
| `GET /api/checklists` | `ChecklistVersion[]`, новые версии первыми внутри чек-листа |
| `GET /api/checklists/:id` | версия по её внутреннему ID |
| `POST /api/checklists/:checklistId/versions` | `ChecklistInput` → новая `ChecklistVersion`, 201 |
| `POST /api/score` | `ScoreRequest` → `ScoreResponse` |
| `POST /api/evaluations` | `{conversationIds,checklistVersionId,force?:boolean}` → 202 `{evaluationIds}` |
| `GET /api/evaluations` | `Evaluation[]`; необязательный фильтр `conversationId` |
| `GET /api/evaluations/:id` | сохранённый статус, ответы, цитаты, баллы и попытки |
| `POST /api/evaluations/:id/retry` | 202 `{evaluationIds:[newId]}`; только для failed |

Пример импорта настоящих данных:

```sh
curl -X POST http://127.0.0.1:3000/api/import \
  -H 'Content-Type: application/json' \
  -d '{"source":"organizer","groupId":"DEV"}'
```

Для контрольного набора передайте выданный организаторами `groupId`. Число записей и состав языков не захардкожены. JSON-импорт принимает `{source:"json",groupId:"DEMO",records:[...]}`, где каждая запись имеет исходные поля `conversation_id`, `channel`, `language`, `transcript`, `audio_url`. Полный вымышленный пример есть в `shared/fixtures.ts`. PDF и произвольный текст напрямую не импортируются.

Каждой реплике назначается стабильный ID `m0001`, `m0002`, … внутри транскрипта. Сохраняются роли, исходные timestamp, язык, канал и URL аудио. Внутренний ID диалога зависит от группы, исходного ID и хеша нормализованной исходной записи. Поле `transcriptHash` включает также канал, язык и URL аудио: изменение любого из них сохраняет новую ревизию. Старые записи не перезаписываются. Одинаковые ID в DEV и CONTROL независимы. Весь пакет проверяется до записи и сохраняется одной транзакцией.

Импорт organizer проверяет HTTP-статус, `isSuccess`, группу, `total_records` и все записи. Таймаут — 30 секунд. Подписанные query-параметры сохраняются; заменяется только `group_id`. Ошибка источника не превращается в успешный пустой импорт.

Ошибки имеют вид `{error:{code,message}}`: 400 — неверный запрос, 404 — нет объекта, 413 — JSON больше 10 MB, 502 — ошибка/некорректный ответ источника, 503 — источник не настроен. В ответ не попадают URL доступа и содержимое ошибочного ответа источника.

## Расчёт баллов

Начальный чек-лист `default` воспроизводит восемь критериев из присланного PDF. В нём есть формулировки, условия N/A и описания каждой ступени шкал. Порог ответа в 3 минуты, теги и вложения не оцениваются.

| ID | Ответ | Вес | N/A |
| --- | --- | ---: | --- |
| contact | boolean | 10 | нет |
| needs | boolean | 15 | да |
| identity | boolean | 20 | да |
| consultation | 0, 5, 10, 15, 20 | 20 | да |
| empathy | boolean | 15 | нет |
| dialogue | 0, 4, 7, 10 | 15 | нет |
| closing | boolean | 5 | да |
| gross | boolean, true означает нарушение | 0 | нет |

```text
q = true → 1, false → 0, числовая оценка → значение / максимум шкалы
total = 100 × Σ(weight × q) / Σ(применимые веса)
```

N/A исключает критерий из обеих сумм; требуется непустая причина и разрешение в конфигурации. При нулевом знаменателе `total=null`. Итог округляется после суммирования до двух знаков. Грубое нарушение сохраняется отдельным флагом, не обнуляет итог и не участвует в знаменателе. Баллы секций — вклад в общий итог; секция без применимых весов имеет `points=null`, `maxPoints=null`. Сумма отображаемых округлённых вкладов может не совпадать с итогом на сотую.

`POST /api/score` получает ID сохранённой версии и ровно один ответ на каждый её критерий. Пример:

```ts
import { scoreExampleAnswers } from './shared/fixtures';
const versions = await fetch('/api/checklists').then(r => r.json());
const response = await fetch('/api/score', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({
    checklistVersionId: versions.find(v => v.checklistId === 'default').id,
    answers: scoreExampleAnswers,
  }),
});
// Для исходного чек-листа: total=85.38, applicableWeight=65.
```

Этот маршрут проверяет допустимость значений и считает баллы. **Он не читает диалог, не проверяет смысл причины N/A и ссылки на доказательства, не вызывает LLM и не сохраняет AI-оценку.** Для полного анализа используйте `/api/evaluations`. Редактирование чек-листа создаёт новую версию, старую можно получить по прежнему ID.

## Подключение Gemini

Нужны API-ключ из [Google AI Studio](https://aistudio.google.com/apikey), точный ID доступной этому проекту модели с поддержкой structured output и рабочая квота. Сам факт наличия ключа не гарантирует доступ к конкретной модели. Если используется платный API, сначала согласуйте бюджет пробного запуска; стоимость зависит от модели и фактического количества токенов.

В существующий `.env` добавьте следующие строки, сохранив `ORGANIZER_API_URL`:

```dotenv
AI_PROVIDER=gemini
GEMINI_API_KEY=your_api_key
GEMINI_MODEL=your_available_model_id
AI_MAX_OUTPUT_TOKENS=8192
```

После изменения `.env` перезапустите сервер. Не используйте префикс `VITE_` для ключа и не помещайте его в shared или браузер. Для режима без модели оставьте `AI_PROVIDER=none`: импорт и чтение сохранённых результатов доступны, новая AI-оценка возвращает 503. Неполная явно включённая конфигурация Gemini останавливает запуск с ошибкой конфигурации.

Адаптер явно закреплён за Gemini Developer API (`generativelanguage.googleapis.com`). Сторонние переменные SDK для Vertex AI/enterprise и base URL его не переключают. Vertex AI потребует отдельной настройки/адаптера.

Вначале оцените **один** диалог, передав его внутренний `id` из `/api/conversations` и `id` версии из `/api/checklists`:

```sh
curl -X POST http://127.0.0.1:3000/api/evaluations \
  -H 'Content-Type: application/json' \
  -d '{"conversationIds":["CONVERSATION_ID"],"checklistVersionId":"CHECKLIST_VERSION_ID"}'

curl http://127.0.0.1:3000/api/evaluations/EVALUATION_ID
```

Затем вручную сопоставьте ответы и доказательства с транскриптом. Только после проверки доступа, квоты и качества запускайте весь DEV. Для моделей другого провайдера предусмотрен интерфейс `EvaluationProvider`; готовый облачный адаптер сейчас только Gemini.

## Как работает AI-оценка

1. Сервер сохраняет задачу в SQLite и возвращает её ID. UI опрашивает `GET /api/evaluations/:id` до `completed` или `failed`.
2. Очередь выполняет максимум два запроса одновременно. Каждый запрос получает весь выбранный чек-лист, его шкалы и правила N/A, а также реплики с исходными ID. Текст диалога передаётся как недоверенные данные, отдельно от инструкций оценщику.
3. Модель возвращает structured JSON с ответом и объяснением по каждому критерию, `evidenceMessageIds`, `checkedSpanMessageIds` и причиной N/A. Она не вычисляет итоговый балл.
4. Сервер проверяет полное покрытие критериев, допустимые значения, N/A с причиной, непустое обоснование и наличие реальных ID доказательств. Неполная генерация также отклоняется. Цитаты извлекаются из сохранённых реплик, а не из текста, сочинённого моделью.
5. Проверенный модуль считает баллы; ответы, точные цитаты, итог, версия чек-листа, модель, версия инструкций и история вызовов сохраняются до перехода к следующей задаче.

`originalAnswers` / `originalScore` — неизменяемый исходный результат AI; `effectiveAnswers` / `finalScore` учитывают решения по апелляциям. `evidence` содержит оригинальные реплики в двух массивах: `evidence` и `checkedSpan` по каждому критерию. Их ID позволяют интерфейсу перейти к исходному сообщению.

Один сетевой запрос ограничен 90 секундами. Разрешены максимум два повтора транспортных ошибок за всю оценку и одна попытка исправления некорректного JSON/ответов/доказательств — максимум четыре вызова суммарно. Ошибки авторизации и отсутствующей модели автоматически не повторяются. Учитывается `Retry-After`; если источник требует ждать больше 60 секунд, задача завершается ошибкой вместо преждевременного повторного запроса. SDK retries и automatic continuation отключены, чтобы число вызовов было наблюдаемым.

В `attempts` сохраняются длительность, статус, безопасный код ошибки, фактическая версия модели, когда она доступна, и предоставленные API счётчики токенов. `usage.calls` включает все попытки; суммарный счётчик токенов равен `null`, если хотя бы для одной попытки он неизвестен. Таймаут клиента не гарантирует прекращения обработки на стороне провайдера; такие расходы могут отсутствовать в полученном usage. Числовая стоимость пока не вычисляется: тариф не захардкожен.

Диагностика каждой попытки доступна в `GET /api/evaluations/:id` и списке оценок:

- `failureStage`: `provider` (включая TIMEOUT), `finish_reason`, `json_parse`, `schema`, `answers`, `evidence` или `interrupted` (восстановление после перезапуска); `null` у успешной/выполняющейся попытки или при отсутствии исторических данных.
- `finishReason`: значение провайдера, например `STOP`, `MAX_TOKENS` или `CONTINUATION`; сохраняется также при успешной оценке. `null`, если ответ не получен или провайдер не передал поле.
- `validationErrors`: массив `{code, path, message}` с причиной и путём из строк/индексов. Например, `{"code":"INVALID_LEVEL","path":["answers",3,"value"],"message":"Expected one of 0, 5, 10, 15, 20 for criterion consultation"}`. Индекс относится к порядку ответов модели, даже если он отличается от порядка критериев. Пустой путь `[]` означает ошибку JSON в корне; `['finishReason']` относится к метаданным генерации.

Для Zod сохраняются все найденные ошибки схемы, включая причины отказа вариантов union. Проверки ответов и evidence сохраняют первую найденную ошибку. Ошибки синтаксиса JSON сохраняют сообщение парсера и позицию, когда она доступна; фрагменты ответа в сообщении убираются. Произвольные исключения SDK не попадают в диагностику. При TIMEOUT/ошибке провайдера и при успехе `validationErrors=[]`. Последующие повторы не заменяют диагностику предыдущих попыток. После перезапуска новые поля сохраняются; старые записи без них читаются с `null`/`[]`, их прежнюю точную причину восстановить нельзя.

При перезапуске завершённые результаты остаются, прежние `running` становятся `failed/INTERRUPTED`, задачи `queued` продолжаются с той же конфигурацией провайдера. При несовпадении модели, настроек или версии инструкций задача получает `PROVIDER_CHANGED`. Явный retry создаёт **новую** запись с `retryOfId`, сохраняя историю старой. Retry завершённого результата возвращает 409.

Повторный запуск с теми же диалогом, версией чек-листа, провайдером/моделью, конфигурацией и версией инструкций возвращает прежнюю completed/queued/running задачу. Группы изолированы. Для нового вызова модели укажите `force:true`. Кэш не доказывает повторное выполнение: в UI показывайте сохранённый `createdAt` и статус. Если облачный провайдер обновил модель под тем же alias, для перепроверки используйте `force:true` или отдельный точный model ID.

**Границы проверки:** реальные ID доказывают существование цитат, но не смысловую правильность оценки. Корректность N/A, наличие нарушения и соответствие Ground Truth проверяются отдельно вручную. Справочник продукта ещё не предоставлен; модель просят не выдумывать тарифы и прямо указывать, если факт невозможно проверить по диалогу. Prompt-защита от инструкций внутри реплик снижает риск, но не даёт гарантии устойчивости модели.

Интеграционные тесты проверяют официальный SDK с тестовым HTTP-транспортом, очередь, восстановление, валидацию и сохранение. Они **не подтверждают** доступ конкретного ключа, качество ответов реальной модели или её точность на RU/KZ/EN. Реальные платные запросы при реализации этого этапа не выполнялись.

## Апелляции

Обращение относится к одному критерию завершённой оценки. Одна pending-апелляция на пару evaluation/criterion; повторная отправка возвращает 409. После решения можно создать новое обращение, сохранив предыдущую историю. Авторизация и проверка личности проверяющего в этом прототипе не реализованы.

| Маршрут | Тело / результат |
| --- | --- |
| `POST /api/appeals` | `{evaluationId,criterionId,comment}` → 201 `Appeal` |
| `GET /api/appeals` | история `Appeal[]`; фильтры `evaluationId`, `status=pending\|resolved` |
| `GET /api/appeals/:id` | одно обращение с решением и снимками до/после |
| `POST /api/appeals/:id/decision` | `DecisionInput` → обновлённый `Evaluation` |

Создание:

```json
{"evaluationId":"EVALUATION_ID","criterionId":"consultation","comment":"Все вопросы клиента были решены"}
```

Подтверждение текущего ответа:

```json
{"decision":"confirm","reason":"Проверил реплики: исходная оценка обоснована"}
```

Изменение:

```json
{"decision":"change","replacementValue":20,"reason":"Оператор ответил на оба вопроса клиента"}
```

`reason` обязателен и не может состоять из пробелов. `replacementValue` проверяется по **версии чек-листа, которой выполнена оценка**. Для N/A передайте строку `"NA"`; причина решения используется как `naReason`. Для boolean передавайте JSON `true/false`, для шкалы — разрешённое число. Запрещённый N/A или неверная ступень возвращают 400 и ничего не сохраняют. Повторное решение закрытого обращения возвращает 409.

Решение и обновлённый результат записываются одной транзакцией. `originalAnswers`, `originalScore`, исходные `evidence`, модель и история вызовов не меняются. Изменяется только выбранный элемент `effectiveAnswers`, затем весь `finalScore` пересчитывается общим модулем, включая N/A и флаги. Другие уже принятые исправления сохраняются. Gemini при пересмотре не вызывается.

У изменённого ответа `explanation` — причина проверяющего, а ссылки на AI-доказательства очищены: прежние цитаты не выдаются за доказательство новой оценки. Исходные цитаты по-прежнему доступны в `evidence`. UI должен показывать их как исходные и рядом выводить причину решения из истории апелляций.

`Appeal` сохраняет `beforeAnswer` при создании и `afterAnswer` после решения, решение/причину и даты. `scoreBefore`/`scoreAfter` — итог непосредственно до/после решения, до разрешения оба null. Это важно, если между созданием и решением рассмотрели другой критерий. История доступна после перезапуска сервера. Закрытые обращения не редактируются.

## Следующий этап

Настроить ключ и модель, чтобы запустить оценивание с веб-экрана. Для проверки качества отдельно прогнать RU/KZ/EN и транскрипт звонка. `/api/evaluations` и `/api/appeals` реализованы.

По обновлённым правилам главный критерий отбора — близость к Ground Truth на 10 ранее неизвестных транскриптах. Текущие тесты проверяют программную обработку результатов, **не точность AI**. Нужны ручные эталонные примеры RU/KZ/EN и отдельная выборка для проверки без подстройки. Официальная формула сравнения с Ground Truth пока не предоставлена.

На проверке реального DEV-источника 7 ноября 2026 получено 65 записей: RU 35, KZ 15, EN 15; чаты 60, звонки 5. Реальные диалоги не входят в fixtures или Git. Сервер по умолчанию доступен только локально; авторизация и публичное развёртывание в этом этапе не реализованы.
