Обновление правил: контроль содержит 10 неизвестных транскриптов, основное внимание — совпадению AI-оценок с Ground Truth; официальная метрика не предоставлена. > **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** За 24 часа создать прототип CQA с редактируемым чек-листом, оценкой диалогов с доказательствами и апелляцией с сохраняемой историей.

**Architecture:** Один Express-сервер обслуживает HTTP API, импорт, небольшую очередь оценивания, проверку ответа LLM, расчёт баллов и SQLite. Одинаковая поддерживаемая Node.js LTS на двух компьютерах; версии зависимостей фиксируются lockfile. Основной кандидат LLM: gemini-3.8-flash; доступ конкретного ключа, квота и качество на трёх языках проверяются в первый час. API-ключ и бюджет пока пользователем не подтверждены.

## Global Constraints

- Пользователь берёт backend. Второй участник берёт frontend; его владение React является рабочим предположением.
- DEV: 65 диалогов, 60 синтетических чатов и 5 реальных звонков; 35 RU, 15 KZ, 15 EN. Транскрипты уже даны.
- Оценивать оператора; client, bot и system сохранять как контекст. Сохранять исходные timestamp: MM:SS для чатов, ISO 8601 с часовым поясом для звонков.
- Пользователь изменяет и добавляет критерии, формулировку, вес, тип ответа, допустимость N/A и числовую шкалу. Изменение работает без правки кода.
- По каждому критерию нужны значение, баллы, вес, объяснение и доказательство. При пропуске действия нужен проверенный участок; при N/A нужна причина. Предусмотреть результаты секций.
- contact: boolean, вес 10; needs: boolean/N/A, 15; identity: boolean/N/A, 20; consultation: {0,5,10,15,20}/N/A, 20; empathy: boolean, 15; dialogue: {0,4,7,10}, 15; closing: boolean/N/A, 5; gross: boolean, без баллов.
- N/A: needs — информации изначально достаточно; identity — запрос не требует проверки личности; consultation — запрос не сформулирован до окончания чата; closing — чат оборвался до возможности завершения.
- Gross=true означает обнаруженное нарушение. Флаг не обнуляет числовой итог и не включается в веса.
- Итог: 100 * sum(weight * normalizedValue) / sum(applicableWeight). Binary=true/false -> 1/0; scale -> raw / max(levels). N/A исключён из обеих сумм. Округлять итог до двух знаков; при нулевом знаменателе возвращать null, а не 0.
- Порог первой реакции в 3 минуты, теги и вложения не оцениваются.
- Апелляция относится к критерию. Решение проверяющего с причиной подтверждает или меняет оценку. Исходная оценка, решение и финальный результат доступны после перезагрузки.
- Авторизация не нужна. Разные действия автора апелляции и проверяющего не означают реализованное разграничение доступа.
- T+23 часа: открываются контрольные транскрипты и новый group_id; T+24: стоп-код, последний commit фиксируется. После него обработка данных и редактирование чек-листа через готовый UI разрешены.
- До стоп-кода: открытый Git-репозиторий, README с запуском, заранее отправленная организаторам ссылка. Отправку выполняет команда; этот план ничего не отправляет и не публикует.
- Защита до 5 минут: интерфейс 1 мин; оценка, доказательство, N/A и итог 2 мин; апелляция 1 мин; изменение критерия 1 мин. Для платной модели указать название и стоимость оценки с учётом всех вызовов.
- Требуется возможность будущей адаптации интерфейса как HTML-компонента Dynamics 365; готовая интеграция с Dynamics в эти сутки не входит.

## Review Focus

- Новая версия критерия не должна менять старые результаты и попадать в кэш старой конфигурации; проверка в задачах 1 и 4.
- Несуществующий ID реплики, запрещённый N/A и недопустимая ступень шкалы должны давать ошибку оценки, а не правдоподобный результат; проверки в задачах 2 и 3.
- Одинаковые conversation_id разных group_id и повторный импорт должны сохранять корректные связи с результатами; проверка в задаче 1.
- Перезапуск во время оценки и ошибка одного запроса не должны терять завершённые результаты или останавливать остальные; проверка в задаче 3.
- Апелляция должна менять только финальную оценку выбранного критерия и сохранять исходные данные; проверка в задаче 5.

## Shared interfaces

Имена во всём плане едины; TypeScript-контракты создаются до разделения задач.

- `CriterionConfig`: id, sectionId, title, instruction, answerType (`binary|scale`), scoringMode (`weighted|flag`), weight, levels (`number[]`), allowNA, naRule.
- `ChecklistVersion`: id, checklistId, version, title, sections, criteria, createdAt. Сохранение создаёт неизменяемую версию.
- `Message`: id, timestamp, speaker (`client|operator|bot|system`), text. ID вида m0001 назначается один раз в неизменяемом транскрипте; timestamp не генерирует модель.
- `Conversation`: id (внутренний), groupId, sourceConversationId, transcriptHash, channel, language, messages, audioUrl.
- `CriterionAnswer`: criterionId, value (`boolean|number|"NA"`), explanation, evidenceMessageIds, checkedSpanMessageIds, naReason.
- `ScoreSummary`: total (`number|null`), sections (`{sectionId,points,maxPoints}[]`), contributions, grossViolation. Баллы и максимум секции выражены во вкладе в общий итог100 с тем же глобальным знаменателем; секция без применимых weighted критериев обозначается как неприменимая. Исходные ответы модели и эффективные ответы после решений различаются.
- `Evaluation`: id, conversationId, checklistVersionId, modelId, promptVersion, status (`queued|running|completed|failed`), originalAnswers, effectiveAnswers, originalScore, finalScore, usage, error.
- `Appeal`: id, evaluationId, criterionId, comment, status (`pending|resolved`), decision (`confirm|change|null`), replacementValue, reason, createdAt, resolvedAt.
- `SourceRecord`: conversation_id, channel (`agent chat|voice call`), language (`RU|KZ|EN`), transcript (`{timestamp,speaker,text}[]`), audio_url (`string|null`); это исходный формат API, не Conversation.
- `ImportSummary`: imported (`number`), existing (`number`), groupId (`string`). Organizer-адаптер проверяет isSuccess и data.records и передаёт groupId источнику как параметр `group_id`.
- `ChecklistInput`: title, sections (`{id,title}[]`), criteria (`CriterionConfig[]`); служебные id/version/createdAt назначает сервер.
- `ProviderResult`: answers (`CriterionAnswer[]`), modelId, usage (доступные счётчики входных/выходных/thinking токенов и всех вызовов), durationMs. Счётчики не выдумываются при отсутствии usage в ответе.
- `DecisionInput`: decision (`confirm|change`), replacementValue (`boolean|number|"NA"`, обязательно при change), reason (непустая строка).

Четыре таблицы: conversations, checklist_versions, evaluations, appeals. Конфигурацию критериев и результаты для MVP хранить JSON-полями; связи задавать внешними ключами. Импорт одной группы не переписывает транскрипт, на который уже есть оценка. Идентичные повторные импорты распознавать по groupId + sourceConversationId + transcriptHash.

## HTTP contract

| Route | Request / result |
|---|---|
| POST /api/import | `{source:"organizer",groupId}` или `{source:"json",records}` -> `{imported,existing,groupId}` |
| GET /api/conversations | фильтры groupId/language/channel -> список |
| GET /api/conversations/:id | Conversation и ссылки на доступные оценки |
| GET /api/checklists | список сохранённых версий |
| POST /api/checklists/:checklistId/versions | конфигурация -> новая ChecklistVersion |
| POST /api/evaluations | `{conversationIds,checklistVersionId}` -> HTTP202 `{evaluationIds}` |
| GET /api/evaluations/:id | Evaluation, включая status и итог |
| POST /api/evaluations/:id/retry | повтор failed-оценки без потери старой диагностики |
| GET /api/appeals | список обращений |
| POST /api/appeals | `{evaluationId,criterionId,comment}` -> Appeal |
| POST /api/appeals/:id/decision | `{decision,replacementValue?,reason}` -> обновлённая карточка оценки |

Некорректный запрос -> 400; неизвестный ID -> 404; повторное решение уже закрытой апелляции -> 409. Ошибка импорта не превращается в пустой успешный набор. UI опрашивает выполняемую оценку примерно раз в секунду и останавливает polling после completed/failed.

## Screen structure (read-only IA handoff, STANDARD)

Общая навигация: Диалоги / Чек-листы / Апелляции. Первичные объекты: диалог с оценкой, версия чек-листа, апелляция; доказательство является частью оценки. Роли действий показываются через форму апелляции и панель проверяющего; логина нет.

| Surface / route | Job, ownership, transitions and recovery |
|---|---|
| dialogs `/dialogs` | Импорт по groupId или JSON, фильтры языка/канала/группы, одиночная и пакетная оценка. Открывает dialog. Состояния: пусто, загрузка, импорт не удался с повтором, записи с queued/running/completed/failed. |
| dialog `/dialogs/:id?evaluation=:evaluationId` | Транскрипт и аудио, выбор версии чек-листа, запуск, критерии/веса/баллы/секции/итог/gross, исходный и финальный результаты. Anchor `#m0001` прокручивает и выделяет источник. Ошибка оценки с повтором; сохранённая оценка читается без вызова LLM. |
| checklists `/checklists` | Создать/изменить критерий, тип, ступени, вес, N/A и секцию, сохранить новую версию. Ошибки полей показываются до сохранения; отмена возвращает прежнюю версию, открытые старые оценки сохраняются. |
| appeals `/appeals` | Очередь pending/resolved; выбранная строка ведёт в dialog с query `appeal=:appealId`, где открывается ReviewPanel. Решение требует причины, затем показываются исходное значение, решение, итог. |
| appeal-form, overlay внутри dialog | Контекстный ввод комментария по выбранному критерию, подтверждение сохранения, ошибка с сохранением введённого текста. |
| review-panel, contextual panel внутри dialog | Отдельное действие проверяющего: подтвердить/изменить допустимое значение и обосновать решение. После сохранения обновляется финальный результат. |

Основной viewport — ноутбук; на узкой ширине две колонки карточки складываются в одну с сохранением навигации к доказательству и апелляции. Не добавлять отдельный аналитический dashboard, метрики уверенности или технические токены/провайдера в основной пользовательский процесс. Название модели и затраты записываются для README/защиты.
